# API Debuggability

Make a production failure answer three questions quickly: what failed, what the
client should do, and which server logs belong to the request. Keep private
implementation details in structured logs, not in the response body.

## Correlation contract

- Preserve the request ID generated by `nestjs-pino`.
- Return it in the `X-Request-ID` response header for success and failure paths.
- When changing the response envelope, prefer exposing the same value as
  `requestId`; never generate a second correlation ID inside a filter.
- Ask frontend/support to report the request ID, timestamp, method, and path.
- Bind application log lines to the request logger so they inherit the request ID.

See [[standard-logging]] before changing request logging or redaction.

## Separate human and machine information

- `message` is human-readable and may change.
- `statusCode` communicates HTTP semantics.
- `error` remains the standard HTTP label.
- `code` is an optional stable domain identifier used only when the client must
  branch into a different recovery flow.
- Never make client logic compare `message`.

```ts
export enum ErrorCode {
  ActorTokenInvalid = 'ACTOR_TOKEN_INVALID',
  DuplicateBarcode = 'DUPLICATE_BARCODE',
}
```

Add a code only when equal HTTP statuses need different client actions. Keep
codes centralized per [[standard-constants-no-hardcode]]. Adding decorative codes
for every message creates a second contract without value.

## Actionable client errors

For expected 4xx failures, state the domain subject and cause:

```ts
throw conflict(`Barcode ${barcode} already exists`);
throw notFound(`Product ${barcode} not found`);
```

When structured details are introduced, expose only safe fields that help the
client associate an error with an input:

```ts
{
  code: 'VALIDATION_FAILED',
  errors: [
    { field: 'barcode', rule: 'isNotEmpty', message: 'Barcode is required' },
  ],
}
```

Keep the existing error contract backward compatible unless a coordinated
contract migration explicitly changes it. Do not silently change `message` from
`string | string[]` to another shape.

## Database errors

- Prefer explicit domain checks for user-correctable uniqueness and FK failures.
- Keep PostgreSQL error mapping in `AllExceptionsFilter` as the race-condition
  safety net.
- Map known constraint names to stable, safe domain messages/codes.
- Do not return SQL, table names, constraint details, driver messages, query
  parameters, or stack traces.
- Log the original exception server-side with the request ID and redacted context.
- Preserve the correct HTTP status: conflict for uniqueness, bad request or
  unprocessable entity for invalid references according to the existing contract.

Do not parse a database error's human-readable text when PostgreSQL exposes a
stable code or constraint field.

## Logging diagnostic context

Log identifiers, not entire objects:

```ts
request.log.warn(
  { operation: 'product.create', barcode, userId },
  'Product creation rejected',
);
```

Include fields useful for searching: operation, user/actor ID, relevant entity
ID, safe filter summary, and error class/code. Never log credentials, cookies,
tokens, PINs, hashes, personal data without need, or complete request bodies.

Use levels consistently:

- `debug`: development diagnostics that are normally disabled in production.
- `info`: successful domain milestones worth retaining.
- `warn`: expected rejection or degraded behavior that needs visibility.
- `error`: unexpected failure or 5xx, including the original stack.

Do not double-log the same exception in a service and the global filter unless
the service log adds distinct domain context.

## 5xx behavior

- Return a generic public message and the request correlation value.
- Log the full original error once through the request-bound logger.
- Redact sensitive request fields before logging.
- Do not catch an exception only to replace it with a context-free error.
- Preserve `cause` when wrapping an error for internal logging.

## Verification

Test at least:

- one validation failure;
- one not-found or conflict;
- one known PostgreSQL constraint failure;
- one unexpected exception;
- presence and consistency of `X-Request-ID`;
- omission of stack, SQL, secrets, and raw driver details;
- preservation of any machine-readable code required by the frontend.
